# 前端转 Java 后端，我是怎么排学习顺序的

我是一个写 Vue 的，因为工作需要开始啃 Java 后端。

一开始我犯了个典型错误：打开项目，找了个最核心的业务类开始读。结果一屏代码里塞着事务注解、第三方支付调用、状态流转、异常处理、并发锁——**每个词我都认识，连起来完全不知道在干嘛**。

后来我换了策略，先给自己排了一条路线。这篇就讲讲这条路线是怎么设计的，以及为什么我建议你也别从核心业务开始。

> 先说明：这篇文章只讲学习路线的设计逻辑，不涉及任何具体项目代码。举的例子都是通用的。

## 一、先认识一个残酷现实：Java 项目的层次比前端多

前端一个功能，通常就是「组件 → 请求 → 渲染」。

Java 后端分层要厚得多：

```
HTTP 请求
   ↓
Controller     ← 接参数、返回结果
   ↓
Service        ← 业务逻辑在这
   ↓
DAO / Mapper   ← 跟数据库打交道
   ↓
数据库
```

新手最容易困惑的不是"哪一层干什么"，而是**同一个东西会在好几层各出现一个版本**：

- 前端传上来的叫 `XxxReq`（请求对象）
- 数据库里存的那份叫 `Xxx` 或 `XxxEntity`（实体）
- 返回给前端的叫 `XxxVO`（展示对象）

**为什么不能一个对象从头用到尾？** 因为职责不同：

- `Req` 决定**允许客户端传什么**——不能让前端直接往数据库字段上写
- `Entity` 对应**表结构**，跟数据库一一映射
- `VO` 决定**对外展示什么**——有些字段内部用但不能给前端看

理解了这一点，很多"为啥要复制来复制去"的疑惑就通了。

## 二、为什么别从核心业务开始

核心业务类（订单、支付、结算这类）有个共同特征：**它把所有难点都混在一起了**。

我数过，一个典型的支付实现类里同时存在：

| 维度 | 涉及的知识 |
|---|---|
| 数据访问 | 条件构造器、分页、多表关联 |
| 事务 | `@Transactional` 传播行为、回滚边界 |
| 远程调用 | Feign、服务发现、超时重试 |
| 状态管理 | 状态机、幂等、并发控制 |
| 异常处理 | 全局异常、业务异常码 |
| 安全 | 签名验证、回调验签 |

**六个知识点叠在一起，你根本分不清哪个报错是哪个引起的。** 这就像刚学 Vue 就去读一个 2000 行的巨型组件——能读懂才怪。

### 我的做法：找最简单的 CRUD 链路先跑通

我在项目里找了个**只有一张表、没有任何远程调用、没有事务嵌套**的查询功能。

就这么一个"列表查询"，走完全流程也是完整的：

```
HTTP 请求
   ↓
Spring MVC 匹配到 Controller
   ↓
Spring 创建请求对象，把 HTTP 参数填进去
   ↓
Controller 调用 Service
   ↓
Service 构造查询条件
   ↓
DAO 执行 SQL
   ↓
结果逐层返回
```

**这一条链路跑通，Controller / Service / DAO 的职责分工就清楚了。** 而且因为简单，出问题你立刻知道是哪一步。

## 三、这条路线（按我的实际顺序）

前面几步是"读代码"，后面才开始碰真难点。

### 阶段一：读懂一条完整链路

**这一步在解决什么**：搞清"代码是谁调用的"。前端习惯了「我写的函数我调用」，后端里**你的代码大量是被框架调用的**——想不通这点，看什么都是悬空的。

**会卡在哪**：`interface` 和实现类长得像双胞胎，搞不懂为什么要写两遍。

**具体内容**：

1. **`interface` 与 `implements`** —— 声明与实现为什么要分开
2. **`extends` 继承与泛型类型参数** —— `XxxServiceImpl<XxxDao, Xxx>` 里那两个占位符替换成了什么
3. **完整调用链走一遍** —— 从 HTTP 入口一路看到 SQL

### 阶段二：学会"怎么查"

**这一步在解决什么**：后端 80% 的活是查数据。搞不定查询条件，就只能写死 SQL 或者到处贴代码。

**会卡在哪**：方法引用那个写法看着奇怪——`Xxx::getField` 到底传的是啥？

**具体内容**：

4. **条件构造器** —— `eq`（等于）、`like`（模糊）、`orderByDesc`（排序）怎么拼
5. **字段映射** —— 为什么用方法引用而不是直接写列名字符串
6. **分页原理** —— 别只会调 API

### 阶段三：学会"怎么传数据"

**这一步在解决什么**：数据在系统里会"变身"好几次——前端传的、数据库存的、返回给前端的，**是三份不同的东西**。想清它们的边界，才不会到处 `new` 对象乱塞。

**会卡在哪**：到处在复制对象，`BeanUtil.copyToList()` 这种调用看得一头雾水，觉得"干嘛不直接用同一个"。

**具体内容**：

7. **`Entity` / `DTO` / `Req` / `VO` 的区别** —— 各自该出现在哪一层
8. **对象转换** —— 谁负责把 `Entity` 变成 `VO`
9. **统一返回结构** —— 为什么要有 `RestResponse` 这种东西
10. **参数校验与全局异常** —— 别让参数错误穿透到 Service

### 阶段四：开始碰后端真正的难点

**这一步在解决什么**：前面三个阶段加起来，其实只是"**能看懂、能改简单功能**"。真正让后端区别于前端的东西，全在这一阶段。

**会卡在哪**：这阶段的知识点**互相纠缠**，单独学一个都懂，放一起就乱。

**具体内容**：

11. **Spring Bean 与依赖注入** —— 对象到底是谁 new 的
12. **事务** —— 传播行为、失效场景
13. **远程调用与服务发现** —— Feign、注册中心
14. **业务主流程**（订单、支付、回调）
15. **状态机、签名验签、幂等与并发**、定时任务与失败重试

> ⚠️ **不要跳级**。我一开始就是直接扎进阶段四的核心类，结果六个知识点同时压过来，一个都学不透。阶段一二三是地基，不是拖延。

**注意顺序**：阶段一~三加起来，其实只是"能看懂、能改简单功能"。真正的难点全在阶段四。**这不是拖延，是必须的地基。**

## 四、踩过的坑

### 坑 1：用前端思维硬套 Java

学泛型的时候我第一反应是"这不就是 TypeScript 的泛型嘛"，然后就开始套。

**能套一部分，但有个关键差异**：Java 泛型有**类型擦除**——编译期检查完，运行时那个类型信息就没了。所以你不能在运行时判断 `List<String>` 还是 `List<Integer>`。

TS 的泛型在运行时虽然也不存在，但它编译期约束更强、还能靠类型断言绕；Java 这边绕不过去，得换 `Class<T>` 这种手段传类型。

**结论**：类比是好的入门梯子，但**爬上去之后要把梯子扔掉**。

### 坑 2：以为 Controller 是浏览器直接调的

这个认知卡了我一阵。

真相是：**浏览器只会发 HTTP 文本**（一段字符串），它没法"调用 Java 方法"。

真正干这件事的是 **Spring MVC**——它收到请求后，负责：

1. 找到匹配的 Controller 方法
2. `new` 一个请求对象
3. 把 HTTP 参数一个个填进去（调 Setter，顺便做类型转换）
4. **调用**那个 Java 方法

所以 `Controller` 方法的直接调用方是 **Spring MVC**，不是浏览器。浏览器到方法之间隔着一个框架。

想通这点，"参数是怎么进来的""为什么要有 Setter"这类问题就都有答案了。

### 坑 3：想跳过基础直接看核心业务

这个我第一条就说了。**忍住这个冲动**，简单链路跑十条，胜过核心业务硬啃一条。

## 五、给同样转型的你

三句话：

1. **先窄后深**。找最简单的一条链路彻底跑通，别贪多
2. **分清"看得懂"和"能改"**。看懂 CRUD 不代表能碰事务，这中间隔着一整个阶段四
3. **保留前端优势**。别把前端的直觉全丢了——你在数据结构、异步流程上的经验是能迁移的，只是要搞清边界在哪

后端比前端需要更多"为什么会这样"的追问。前端很多问题刷新一下就好，后端不行——**数据落了库，就没有回头路**。
